# Plan: Senior Founder/Co-Founder Role with Full Access

## Context
The user needs to support companies where all key people are founders or senior leaders (not executives), and they need to see everything in the app. Currently, the app has three role types:
- **Founder**: Full access, sees everything including costs
- **FractionalExec**: Limited visibility (no personnel costs), needs approval for allocations
- **Apprentice**: Very limited, task-focused view

## Problem
In early-stage companies, multiple founders or senior partners work together with equal or near-equal access. They need:
1. Full visibility (like Founder role)
2. No approval workflows between them
3. Ability to manage the entire organization
4. Clear identification as senior leadership

The current system only allows one "Founder" role, and making everyone a "Founder" doesn't semantically make sense for co-founders or senior partners.

## Current Architecture

### Database (Supabase)
- **members table**: Has a `role` field (TEXT) with values: 'Founder', 'FractionalExec', 'Apprentice'
- **members table**: Has a `user_id` field linking to auth.users
- No separate "memberships" table - the members table IS the membership table
- RLS policies filter by workspace_id

### Frontend (React Native)
- **role-store.ts**: Manages UI view switching (Founder/FractionalExec/Apprentice views)
- **permissions.ts**: Defines what each role can see/do
- **organization-seed.ts**: OrganizationMember interface with role field
- **Home screen**: Shows different views based on active role

## Solution Approach

### Option 1: Add "SeniorFounder" or "CoFounder" Role ⭐ RECOMMENDED
Add a new role type that has identical permissions to Founder but with different semantics.

**Pros:**
- Clean separation of concerns
- Easy to understand ("this person is a co-founder")
- Follows existing pattern
- Can add different permission nuances later if needed

**Cons:**
- Need to update multiple places (types, permissions, UI)
- Slight code duplication

### Option 2: Add "isSeniorLeadership" Flag
Keep existing roles but add a boolean flag to grant full access.

**Pros:**
- Less invasive change
- More flexible (can elevate any role)

**Cons:**
- Less semantic clarity
- Mixing role with permission level
- Could confuse permission logic

### Option 3: Permission-Based System
Replace roles with granular permissions.

**Pros:**
- Most flexible
- Industry standard for complex systems

**Cons:**
- Major architectural change
- Overkill for current needs
- Would take significant time

## Recommended Implementation: Option 1 (Add "CoFounder" Role)

### Step 1: Add Type Definition
**File: `src/types/index.ts`**
- Update Role type: `'Founder' | 'CoFounder' | 'Apprentice' | 'FractionalExec' | 'Government' | 'Unaffiliated'`
- CoFounder has same permissions as Founder

### Step 2: Update Permissions System
**File: `src/lib/permissions.ts`**
- Add `CO_FOUNDER_PERMISSIONS` (identical to FOUNDER_PERMISSIONS)
- Update `getPermissionsForRole()` to handle 'CoFounder' case
- Update UserRole type to include 'CoFounder'

### Step 3: Update Role Store
**File: `src/lib/state/role-store.ts`**
- Update RoleView type to include 'CoFounder' (or map CoFounder → Founder view)
- Decision: CoFounders should see the same UI as Founders (FounderHome component)

### Step 4: Update Organization Types
**File: `src/lib/organization-seed.ts`**
- Update OrganizationMember interface role type
- Update DEFAULT_SKILLS_BY_FUNCTION if needed

### Step 5: Update Home Screen Routing
**File: `src/app/(tabs)/index.tsx`**
- Update the role switch in HomeScreen() to map CoFounder → FounderHome
```typescript
switch (activeRole) {
  case 'Apprentice':
    return <ApprenticeHome />;
  case 'FractionalExec':
    return <ExecutiveHome />;
  case 'Founder':
  case 'CoFounder': // Both render same view
  default:
    return <FounderHome />;
}
```

### Step 6: Update Supabase Service
**File: `src/lib/supabase-service.ts`**
- Ensure memberService handles 'CoFounder' role correctly in type conversions
- Update any role validation logic

### Step 7: Update UI Components
- **RoleSwitcher**: Show "Co-Founder" option if user has that role
- **Member Creation**: Allow selecting "Co-Founder" when adding team members
- Any permission checks should treat CoFounder === Founder

### Step 8: Database Considerations
- No migration needed! The members.role field is TEXT and already accepts any value
- Just start writing 'CoFounder' to the role field
- Existing 'Founder' roles remain unchanged

## Alternative: "Senior" Prefix Approach
Instead of "CoFounder", we could use "SeniorFounder", "SeniorExec", etc.

Benefits:
- More general (works for non-founders too)
- Clear seniority indication
- Could have different senior roles later

Recommendation: Stick with "CoFounder" as it's more semantically clear for the stated use case.

## Edge Cases to Consider
1. **Who is the "owner" of the workspace?**
   - Original Founder remains the workspace.owner_id (if that field exists)
   - CoFounders have full access but aren't technically the owner

2. **Billing/subscription ownership?**
   - Keep that with the original Founder
   - CoFounders can view but maybe not modify billing (future consideration)

3. **Can CoFounders invite other CoFounders?**
   - Yes, treat them as equal to Founders for permissions

4. **Role naming in UI:**
   - Display as "Co-Founder" (hyphenated, capitalized)
   - Keep code as 'CoFounder' (no hyphen)
