# Task Assignment & Acceptance System - Implementation Plan

## Current State Analysis

**Existing Systems:**
1. **WorkPlan Store** - Tasks have `assignedBy`, `ownerId`, `allocations[]`, `assignedMemberIds[]`
2. **Notification Store** - Generic notification system with `assignment` type
3. **Allocation Request Store** - Approval system for executives requesting apprentice allocations
4. **Ownership & Approval System** - Complete system for AI tools and suppliers (can be adapted)

**Current Gaps:**
- When someone creates a task and assigns it to another person, the assignee is **immediately allocated** without their consent
- No acceptance/rejection mechanism for task assignments
- No clear distinction between "assigned to me" vs "accepted by me"
- No inbox/pending tasks view for reviewing assignments

## Proposed Solution

### 1. Task Assignment State Model

Add new fields to `WorkPlan` interface:
```typescript
interface WorkPlan {
  // ... existing fields ...

  // New assignment tracking fields
  assignmentStatus?: 'draft' | 'pending-acceptance' | 'accepted' | 'rejected';
  assignmentRequests?: TaskAssignmentRequest[];
}

interface TaskAssignmentRequest {
  requestId: string;
  assignedToId: string;
  assignedToName: string;
  assignedById: string;
  assignedByName: string;
  status: 'pending' | 'accepted' | 'rejected';
  message?: string; // Optional message from assigner
  requestedAt: string;
  respondedAt?: string;
  responseNote?: string; // Reason for rejection
}
```

### 2. Task Assignment Flow

**Scenario A: Creating a task and assigning to yourself**
1. User creates task → `ownerId` = current user
2. User adds themselves to `allocations[]` → Immediate, no approval needed
3. Task status: `accepted` (auto-accepted for self-assignments)

**Scenario B: Creating a task and assigning to someone else**
1. Creator creates task → `ownerId` = creator
2. Creator adds Person B to allocations → Creates `TaskAssignmentRequest` with status `pending`
3. Task appears in Person B's "Pending Tasks" inbox
4. Person B can:
   - **Accept** → Adds their allocation, moves to their active tasks
   - **Reject** → Removes allocation, sends notification to creator with reason
   - **Request Changes** → Opens chat/feedback dialog with creator

**Scenario C: Reallocating an existing task**
1. Task owner wants to add/remove people
2. For new people: Creates pending `TaskAssignmentRequest`
3. For removed people: Sends notification, removes allocation
4. Person can accept/reject new assignment

### 7. Key Design Decisions

**Decision 1: Self-assignments don't need approval**
- Rationale: Trust team members to manage their own capacity
- Auto-accept when assigning to yourself

**Decision 2: Pending tasks are visible but locked**
- Rationale: Person can see what's coming but can't start until accepted
- Show in separate "Pending" section, greyed out

**Decision 3: Rejection is respectful and requires reason**
- Rationale: Encourage communication, not ghosting
- Rejection opens feedback dialog
- Rejection sends notification to assigner

**Decision 4: Task creator remains owner**
- Rationale: Creator is accountable for delivery
- Even if rejected, creator can reassign or do themselves

**Decision 5: Bulk accept/reject for efficiency**
- Rationale: If someone has 10 pending, allow bulk action
- Future enhancement: "Accept All" / "Reject All" buttons

### 8. User Experience Flow

**Alice creates task, assigns to Bob:**
1. Alice creates "Design homepage mockup"
2. Alice allocates 5 TU/week to Bob
3. System creates `TaskAssignmentRequest` (pending)
4. Bob gets notification: "Alice assigned you to 'Design homepage mockup'"
5. Bob opens Tasks tab → sees "Pending (1)" badge
6. Bob taps "Pending" → sees task card with Accept/Reject
7. Bob taps "Accept" → Task moves to "Your Tasks", Alice gets notification
8. Bob starts working, TUs count toward utilization

**Bob rejects the task:**
1. Bob taps "Reject"
2. Modal opens: "Why are you rejecting this task?"
3. Bob types: "Currently overloaded with marketing tasks"
4. Bob confirms rejection
5. Alice gets notification with reason
6. Task returns to Alice's ownership, Bob's allocation removed
7. Alice can reassign to someone else or adjust scope
